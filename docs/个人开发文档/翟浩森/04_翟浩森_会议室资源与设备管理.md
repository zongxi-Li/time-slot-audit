## 角色定位

你负责 **resource：会议室资源、分类、设施/设备、开放规则、维护与报修生命周期域** 的全栈开发。

当前系统已有 `meeting_room`、`room_category`、`room_facility`、`room_open_rule` 和只读 `ResourceQueryService`。你的任务是把资源域从“可查询”升级为“可真实管理”，并向预约域提供稳定的资源可预约判定能力。

# 公共执行规范（所有成员必须遵守）

仓库：`https://github.com/zongxi-Li/time-slot-audit.git`

当前团队只保留 `main` 作为共享基线。任何成员**禁止直接在 main 上开发或 push**。开始任务前必须执行：

```bash
git switch main
git pull --ff-only origin main
git status
```

确认工作区干净后，再创建自己的功能分支。所有代码、SQL、测试和文档只提交到自己的 feature 分支，最终通过 Pull Request 合入 `main`，禁止自行 merge `main`。

## Git 提交规范

统一使用 Conventional Commits：

```text
<type>(<scope>): <简短说明>
```

允许的 `type`：`feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`ci`。

`scope` 必须使用当前负责 Domain，例如：`administration`、`identity`、`meeting`、`resource`、`reservation`。公共工程任务可使用 `ci`、`build`、`docs`。

禁止以下提交信息：`update`、`修改`、`完成任务`、`最终版`、`111`。

推荐：

```text
feat(resource): 实现会议室与分类管理
fix(reservation): 限制取消操作仅允许预约本人
refactor(meeting): 收敛签到状态转换逻辑
test(identity): 补充禁用账号与越权场景测试
docs(administration): 补充审批模块接口说明
```

每个 commit 应保持**单一职责、可独立解释、可回滚**。不要把数据库、后端、前端、测试全部堆成一个超大 commit。

## 并行开发约束

1. 不直接访问或修改其他 Domain 的 Mapper / 数据表；跨域写操作必须调用对方公开 Service。
2. 不修改历史 migration；每个成员只新增自己被分配的 migration 文件。
3. 为降低五人并行冲突，本轮 feature 分支**不要直接重写 `sql/schema.sql`**；只新增 migration。最终由组长在集成阶段统一同步完整快照。
4. 不擅自修改冻结的 `core-business-contract.md`。如发现必须改变核心语义，新增 `docs/development/proposals/<domain>-contract-change.md` 并停止相关实现，交由组长评审。
5. 新前端业务代码优先放入 `frontend/src/modules/<domain>/`；避免继续把新业务堆进全局 `stores/`、`views/`、`shared/api/index.ts`。
6. 对 `router/index.ts`、`MainLayout.vue`、全局菜单等共享文件的改动必须小而独立，单独 commit，方便组长处理冲突。
7. 不改别人负责的 UI 页面，不顺手实现其他 Domain 的需求。
8. 不引入 Redis、MQ、微服务、工作流引擎或复杂 RBAC，除非本任务明确要求。
9. API 统一返回 `ApiResponse<T>`；错误码遵守现有全局约定。
10. 预约时间语义继续遵守 `[start,end)`，`PENDING/CONFIRMED` 占用时间，`REJECTED/CANCELLED` 不占用。

## P0：必须完成

### 1. 会议室与分类真实 CRUD

管理员接口包含会议室新增/修改/状态切换、分类查询/新增/修改。要求 ADMIN 才能写；room_name 唯一；capacity 在分类范围内；API 仅暴露 `AVAILABLE/MAINTENANCE/DISABLED`。

### 2. 开放规则管理

实现按会议室维护每周开放规则。weekday 1~7，`close_time > open_time`，当前模型不支持跨日开放。

### 3. 设施/设备管理

至少能真实维护设施名称、数量、描述。

### 4. 统一资源可预约判定

向 reservation 暴露 `ResourceBookingQueryService` 或等价公开契约，返回预约需要的轻量数据：roomId、capacity、status、approvalRequired、maxDurationMinutes、advanceDays、openTime/closeTime 等。reservation 不应依赖 resource 内部 Mapper/Entity。

关键：reservation 事务中的 `meeting_room FOR UPDATE` 必须保持有效，不能因封装导致锁提前释放。

### 5. 前端

新代码放 `frontend/src/modules/resource/`。实现会议室列表/详情、新增/编辑、分类、开放规则、设施、状态切换。

## P1：建议完成

维护计划与设备报修。会议室切换到 MAINTENANCE/DISABLED 时，如果存在未来有效预约，必须返回冲突摘要；resource 不直接取消 reservation。

## 测试要求

覆盖：USER 写资源 403；room_name 唯一；capacity 分类范围；状态枚举映射；开放规则边界；维护状态不可新预约；公开资源契约正确；行锁接口仍可在 reservation 事务内使用。
