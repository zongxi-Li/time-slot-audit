# 会议室预约与时间冲突检查系统 — 接口清单与业务链路附录

> 版本 v1.6 ｜ 代码基线 main@aee20ae ｜ 编制日期 2026-09-15 ｜ 队伍：尖草坪游击队
> 配套《软件概要设计以及详细设计》使用，接口语义与 `docs/development-docs/api-contract-v0.2.md` 一致。

## 1 附录说明

- **统计口径**：后端代码基线为 main 分支 aee20ae 提交（2026-09-15），共 12 个 Controller、**58 个端点**，按 identity、resource、reservation、meeting、administration 五个业务域组织，common 提供统一响应、异常与安全基础设施；数据库共 **14 张业务表**。
- **权限标注约定**：`公开` 无需登录；`USER/ADMIN` 任意登录角色可访问；`ADMIN` 仅管理员角色可访问（`/api/admin` 前缀 + Spring Security 方法级校验兜底）。涉及数据归属的写操作（如取消仅限本人、不能停用自己）在 Service 层做所有权校验。

## 2 接口基本约定

### 2.1 通用约定

| 项目 | 约定 |
| --- | --- |
| 统一前缀 | `/api` |
| 传输格式 | application/json |
| 时间格式 | ISO-8601（`yyyy-MM-ddTHH:mm:ss`） |
| 认证方式 | Bearer JWT；登录接口公开，其余按 USER/ADMIN 授权 |
| 统一成功结构 | `{"code":"SUCCESS","message":"success","data":...}` |
| 统一失败结构 | `{"code":"ERROR_CODE","message":"具体错误信息","data":null}` |
| 幂等控制 | 创建预约以 `requestId` 为幂等键：前端生成 UUID，服务层锁前/锁后双重检查，数据库 `UNIQUE(request_id)` 兜底 |
| 并发控制 | 会议室级行锁（`SELECT ... FOR UPDATE`），隔离级别 READ_COMMITTED，冲突判定用半开区间 `[startTime, endTime)` |

### 2.2 统一错误码

| 错误码 | HTTP | 触发场景 |
| --- | --- | --- |
| VALIDATION_ERROR | 400 | 时间、开放规则、最大时长、容量等参数或业务校验失败 |
| UNAUTHORIZED | 401 | 未登录、JWT 无效或登录凭据错误 |
| FORBIDDEN | 403 | 角色不足或资源所有权不足 |
| RESOURCE_NOT_FOUND | 404 | 用户、会议室或预约不存在 |
| ROOM_UNAVAILABLE | 409 | 会议室维护、停用或资源状态竞争 |
| ROOM_CAPACITY_EXCEEDED | 400/409 | 参与人数超过会议室容量 |
| RESERVATION_TIME_CONFLICT | 409 | 同一会议室存在时间重叠的有效预约 |
| RESERVATION_INVALID_STATE | 409 | 当前状态不允许取消、审批或修改 |
| DUPLICATE_REQUEST | 409 | requestId 与已存在请求业务语义不一致 |
| INTERNAL_ERROR | 500 | 未预期服务器异常 |

## 5 核心业务链路

### 5.1 登录认证链路

登录页（LoginView）提交用户名与密码，经前端 shared/api 统一封装后调用 `POST /api/auth/login`。AuthController 转交 AuthService：按用户名查询 sys_user（UserMapper），校验账号启用状态与 BCrypt 密码摘要，由 JwtService 签发 JWT 并连同用户信息返回。

此后所有业务请求在 Authorization 头携带 Bearer Token，JwtAuthenticationFilter 在进入 Controller 前完成验签、过期检查与身份恢复并写入 SecurityContext。业务 Service 统一通过 CurrentUserProvider（common/security）获取当前用户，不信任前端提交的 userId。

### 5.2 创建预约主链路

入口为预约看板（ReservationBoard）中的新建预约对话框（ReservationDialog）。前端在适配层为每次新建意图生成 requestId（UUID），组装 CreateReservationRequest（不提交 userId 与最终状态）后调用 `POST /api/reservations`。ReservationService 为事务持有者，完整事务步骤如下：

| 顺序 | 事务内操作 | 失败或命中结果 |
| --- | --- | --- |
| 1 | 读取当前认证用户（CurrentUserProvider），按 requestId 幂等预查（findByUserIdAndRequestId） | 命中既有 requestId 时直接返回已创建结果（200） |
| 2 | 预约资格校验（BookingQualificationService.check：账号状态、信用分、限制期） | 无资格返回 FORBIDDEN（403） |
| 3 | 构造 TimeInterval，校验开始早于结束且不跨天 | 参数不合法返回 VALIDATION_ERROR（400） |
| 4 | 锁定 meeting_room 目标行（lockBookableRoom，SELECT ... FOR UPDATE） | 会议室不存在返回 404；同房间竞争请求在临界区串行等待 |
| 5 | 获锁后二次查询 requestId | 覆盖重复请求在锁等待期间已完成的情况（200） |
| 6 | 资源规则校验 validateSlot：AVAILABLE 状态、提前天数、最大时长、容量、开放窗口 | 按规则返回 400 或 409 |
| 7 | 半开区间冲突查询（countConflicts，仅统计 PENDING/CONFIRMED） | 时间重叠返回 RESERVATION_TIME_CONFLICT（409） |
| 8 | 按分类 approvalRequired 决定初始状态（普通 CONFIRMED，受控 PENDING）并插入预约 | UNIQUE(request_id) 唯一键最终兜底 |
| 9 | 提交事务 | 首次创建返回 201；幂等命中返回既有结果 |

跨域依赖：identity 域 BookingQualificationService 提供预约资格判定；resource 域 ResourceBookingQueryService 提供会议室行锁与开放窗口查询。冲突判定采用半开区间语义，有效占用状态仅 PENDING 与 CONFIRMED。首次创建 201，幂等命中 200，时段冲突 409 并触发前端局部刷新日历。

### 5.3 预约改期链路

我的预约（MyReservations）发起改期，调用 `PUT /api/reservations/{id}`。ReservationService 完成所有权与状态校验后，对新时间区间执行与创建相同的规则校验（validateSlot），冲突查询通过 countConflictsExcluding 排除本预约自身；校验通过后按会议室分类的 approvalRequired 重算目标状态（受控分类回到 PENDING，普通分类为 CONFIRMED）。

### 5.4 取消链路

- **用户取消**：`POST /api/reservations/{id}/cancel` 进入 ReservationService.cancel，先经 findByIdForUpdate 行锁定位预约，校验仅预约本人可取消（管理员取消他人预约统一走管理端强制取消通道），且仅 PENDING/CONFIRMED 且尚未开始的预约可取消；取消为逻辑状态变更为 CANCELLED 并记录 cancel_reason，不物理删除。
- **管理员强制取消**：`POST /api/admin/reservations/{id}/force-cancel` 进入 AdministrationService，经 SPI 端口 ReservationLifecyclePort 调用预约域能力完成状态迁移，并写 operation_log 审计。该端口的接入现状见 5.5。

### 5.5 审批链路

预约治理页（AdministrationReservations）对 PENDING 预约执行通过或驳回，调用 `POST /api/admin/reservations/{id}/approve` 或 `/reject`。AdministrationService 先做管理员权限与状态校验（requirePending：仅 PENDING 可操作），驳回意见必填且不超过 500 字；随后经 SPI 端口 ReservationLifecyclePort 调用预约域生命周期服务完成 PENDING → CONFIRMED / REJECTED 的状态迁移，并与 approval_record、operation_log 的写入保持事务一致。

> **现状说明**：端口接口由 administration 域定义（`administration/spi/ReservationLifecyclePort`），注释明确约定由 reservation 域提供委托适配器；reservation 域的 ReservationLifecycleService 已具备 approve、reject、forceCancel 完整能力，但主代码尚未注册该端口的实现 Bean。因此审批、驳回、强制取消三个接口当前运行时统一返回 503（提示预约生命周期服务尚未接入）；单元测试以 Mock 端口打桩通过，故测试未暴露该缺口。恢复链路只需补充一个委托到 ReservationLifecycleService 的适配器类。

### 5.6 会议执行与通知链路

我的会议（MyMeetings）与参会人管理组件（AttendeeManager）调用 `/api/meetings` 下的接口。MeetingExecutionService 对预约上下文的读取一律经 reservation 域 ReservationQueryService 只读完成（校验预约存在性、归属与时间窗），不直接修改预约状态，符合执行域防越权约束；参会人与签到数据写入本域 reservation_attendee 表。

关键动作经 NotificationService 写入 notification 表产生站内通知；前端通知铃（NotificationBell）经 `GET /api/notifications/unread-count` 轮询未读数，支持单条与全部已读。

### 5.7 资源治理链路

会议室管理页（RoomAdmin）经 `/api/admin/rooms` 系列接口进入 RoomAdminService：会议室新增与修改、资源状态切换（AVAILABLE/MAINTENANCE/DISABLED）、设施与开放规则整体替换。分类规则（审批要求、最大时长、提前天数）经 CategoryAdminService 维护；维护计划经 RoomMaintenanceService 管理（PLANNED → FINISHED）。以上全部写入 resource 域自有表，不越界修改预约数据。

### 5.8 报修工单链路

用户侧在会议室页（MeetingRooms）对具体会议室提交报修：`POST /api/rooms/{roomId}/repair-tickets` 进入 RepairTicketService，设施名称按报修时快照保存，工单初始为 OPEN。管理侧报修工单页（RepairAdmin）经 `GET /api/admin/repair-tickets` 查看列表（OPEN 优先），`POST /api/admin/repair-tickets/{ticketId}/resolve` 以条件更新完成 OPEN → RESOLVED 迁移，并发重复处理返回 400。

### 5.9 身份治理与预约资格链路

用户与信用管理页（UserAdmin）经 `/api/admin/users` 系列接口进入 UserAdminService（用户增删改查、启停、重置密码，含不能停用自己、不能降级自己角色等自保护校验）与 UserCreditService（信用分调整、限制期设置，全部写入 user_violation 记录；低于 40 分自动限制 30 天，系统限制在信用恢复至 60 分以上自动解除）。部门经 DepartmentService 维护。

预约资格结论统一由 identity 域 BookingQualificationService 输出（账号状态、信用分阈值、限制期三要素），该服务同时被创建预约主链路调用，使治理规则直接约束业务准入，形成治理到准入的闭环。

### 5.10 统计与审计链路

运营看板（OperationsDashboard）调用 `GET /api/admin/statistics` 获取预约量、使用率等只读聚合指标，统计路径不构成修改业务数据的入口。操作审计页（AuditLogs）调用 `GET /api/admin/audit-logs` 查询关键治理动作（审批、强制取消、资源与分类变更等），并支持 export 接口导出 CSV；审计日志只增不改。
